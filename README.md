# semlex

> **Sem**antic **lex**icon: compile-time OpenTelemetry semantic conventions for
> Rust, straight from your Weaver registry.

Semantic conventions are a lexicon: the agreed words for telemetry. They give
the names of spans, metrics and events, the attributes each one carries, their
types and allowed values, and which ones are required. semlex makes your
[Weaver](https://github.com/open-telemetry/weaver) registry the vocabulary your
Rust code is written in. It expands the registry into Rust at compile time,
with no generated files, and `rustc` checks every call site against it.

## Why it matters

Semantic conventions only pay off when telemetry follows them exactly.
Dashboards, alerts, SLOs, cross-service queries and vendor tooling all match
on exact names, types, units and values. String-keyed instrumentation drifts
silently:

- a typo in a key;
- a status code recorded as a string;
- a required attribute forgotten on one code path;
- a renamed attribute still used in ten services;
- a raw email address;
- a user id on a metric that explodes its cardinality.

Nothing fails. The mistake surfaces weeks later as a broken dashboard, or
never.

With semlex, the registry is enforced by the compiler. Each of those is a
build error at the line that's wrong, saying how to fix it. A rename in the
registry becomes a deprecation warning at every call site.

It is also **AI-forward**. The code reads like the conventions: keys are the
registry's dotted names, so a reviewer or a coding agent sees exactly what the
registry says. The compiler is the spec, and its errors name the attribute,
the signal and the fix, which is the feedback loop an agent needs to get
instrumentation right without guessing. Escape hatches are explicit, warn in
every build, and are listed for review.

## From registry to code

Part of a shop's local registry (the full one is in
[`examples/showcase/registry`](examples/showcase/registry); the `http.*` and
`url.*` attributes come from OpenTelemetry semconv, its upstream):

```yaml
spans:
  - type: http.server.request
    kind: server
    name:
      templates: ['{http.request.method} {http.route}', '{http.request.method}']
    attributes:
      - ref: http.request.method   # an enum: GET, POST, …
        requirement_level: required
        sampling_relevant: true
      - ref: url.scheme
        requirement_level: required
        sampling_relevant: true
      - ref: url.path
        requirement_level: required
      - ref: shop.tenant.code      # annotated `shop.case: upper`
        requirement_level: required
      - ref: http.route
        requirement_level: { conditionally_required: If the request matched a route. }
      - ref: http.response.status_code   # an int
        requirement_level: { conditionally_required: If a response was sent. }

metrics:
  - name: shop.cart.items_sold
    instrument: counter
    unit: '{item}'
    attributes:
      - ref: shop.payment.method   # an enum: card, wallet, invoice
        requirement_level: required
      - ref: shop.tenant.code
        requirement_level: required
```

**Without semlex**, with the OpenTelemetry API directly, this compiles and
runs, and every commented line is wrong:

```rust
let tracer = global::tracer("shop");
let mut span = tracer
    .span_builder("POST /cart/{id}/checkout")
    .with_kind(SpanKind::Server)
    .with_attributes([
        KeyValue::new("http.request.method", "POST"),
        KeyValue::new("url.schema", "https"),                       // typo
    ])
    .start(&tracer);
span.set_attribute(KeyValue::new("http.route", "/cart/{id}/checkout"));
span.set_attribute(KeyValue::new("http.response.status_code", "201")); // string, not int
span.end();                                     // url.path, shop.tenant.code: forgotten

let items = global::meter("shop").u64_counter("shop.cart.items_sold").build(); // no unit
items.add(n, &[KeyValue::new("shop.payment.method", "Card")]);     // not a member; tenant missing
```

**With semlex**, the same instrumentation reads like the registry:

```rust
use crate::{metric, record, span};   // generated by `registry!` in this crate

let span = span!(http.server.request {
    http.request.method: "POST",
    url.scheme: "https",
});
let span = record!(span,
    url.path: path,
    shop.tenant.code: tenant,
    http.route: "/cart/{id}/checkout",
    http.response.status_code: 201,
);
span.end(); // named "POST /cart/{id}/checkout" by the registry's template

metric!(shop.cart.items_sold: n, {
    shop.payment.method: "card",
    shop.tenant.code: tenant,
});
```

The macros come from `registry!` over the shop's **local registry**, in the
same crate. Every mistake in the first version is a compile error in the
second, pointing at the line (abridged):

```text
error[E0425]: cannot find value `schema` in module `__semlex_attr::url`
help: a constant with a similar name exists
  |     url.scheme: "https",

error[E0277]: missing required attribute `url.path` on span `http.server.request`
  = note: set it in `span!`, or with `record!(span, url.path: <value>)` before `end()`

error[E0080]: evaluation panicked: unknown value for `shop.payment.method`; did you mean "card"? Use `custom("…")` for values outside the registry
```

The other checks:
- attributes a signal doesn't define;
- wrong value types;
- sampling-relevant attributes set too late;
- unbounded attributes on metrics;
- unwrapped PII;
- non-stable items without opting in;
- renamed attributes;
- rules from your own registry annotations.

The [showcase](examples/showcase) uses every feature, runs (`cargo run -p
showcase`), and has [a tour of compile errors](examples/showcase/tests/compile_errors)
with rustc's exact output.

It complements `weaver registry live-check`, which checks what reaches the
wire, including telemetry semlex never sees.

**Status:** pre-release and not yet published to crates.io (use a git or
path dependency for now); built and tested against Weaver 0.28 and
OpenTelemetry Rust 0.33. MSRV 1.89.

## Quick start

semlex runs over a **local registry**: one per service or library, holding
the signals that code emits. It pulls what it needs from upstream registries
(OpenTelemetry semconv, your organization's shared conventions) as Weaver
dependencies, so it stays small however large the upstreams are.

1. **Write the local registry** (V2 definitions). Its manifest names the
   upstreams:

   ```yaml
   # registry/manifest.yaml
   file_format: definition_manifest/2.0
   schema_url: https://example.com/schemas/checkout/1.0.0
   stability: development
   dependencies:
     - name: otel
       schema_url: https://opentelemetry.io/schemas/1.44.0
       registry_path: https://github.com/open-telemetry/semantic-conventions.git@v1.44.0[model]
   ```

   Signals in `registry/*.yaml` can `ref:` upstream attributes
   (`http.request.method`) next to their own.

2. **Package it** next to the crate that uses it:

   ```sh
   weaver registry package --v2 -r registry -o . \
       --resolved-registry-uri https://example.com/schemas/checkout/1.0.0/resolved.yaml
   ```

   Commit `resolved.yaml`. Builds read it directly; only packaging needs
   Weaver. To take an upstream change, bump the dependency and re-package.

3. **Expand it in your crate**, at the crate root:

   ```rust
   // src/lib.rs (or main.rs)
   semlex::registry!("resolved.yaml", {
       scope_prefix: "acme.",   // instrumentation scope names: `acme.<crate>`
       visibility: crate,       // macros and modules stay private to this crate
   });
   ```

   ```toml
   [dependencies]
   semlex = "…"

   [dev-dependencies]
   semlex = { version = "…", features = ["testing"] }
   ```

   Several crates in one workspace can share a local registry instead: put
   `registry!` in a small `*-semconv` crate they depend on (the showcase does
   this). See [Setup](docs/guide.md#setup).

4. **Initialize** once at startup, in the application, with your
   OpenTelemetry SDK providers (`opentelemetry_sdk`'s `SdkMeterProvider`,
   `SdkTracerProvider` and `SdkLoggerProvider`, configured with your
   exporters):

   ```rust
   semlex::init(semlex::Config::new()
       .with_meter_provider(meters)
       .with_tracer_provider(tracers)
       .with_logger_provider(loggers))?;
   ```

   Then instrument with `span!`, `record!`, `metric!`, `event!`, `entity!`,
   `attrs!` and the log macros (`info!`, `warn!` …): `crate::span!`, or
   `use crate::{record, span};`. Call the log macros by path
   (`crate::warn!`) where `tracing`'s are also in scope.

   The logger provider carries `event!` and exceptions (log-based
   `exception` events). The log macros need the `tracing` bridge
   (`opentelemetry-appender-tracing`). In a library, don't call `init`:
   [Where telemetry goes](docs/guide.md#where-telemetry-goes) has what
   application and library authors each need to set up.

5. **Test** that the signals are emitted:

   ```rust
   #[test]
   fn request_is_traced() {
       let t = semlex::testing::Telemetry::init();
       handle_request("/users/42");
       crate::assert_span!(t, http.server.request { http.route: "/users/{id}" });
   }
   ```

## In your workspace

**Build cost.** `registry!()` runs at proc-macro speed, unoptimized in dev
builds by default. Add this to your workspace's root `Cargo.toml`; it roughly
halves the time `registry!` takes:

```toml
[profile.dev.build-override]
opt-level = 3
```

**Escape hatches: `unregistered(…)` and `extra(…)`.** An attribute that
isn't in the registry needs `unregistered("key"): value`; a registry attribute
the signal doesn't define needs `extra(key): value`. Both warn at the key in
every build. To deny them in CI, put this in your workspace's `clippy.toml`
and run clippy with `-D warnings`:

```toml
disallowed-methods = [
    { path = "semlex::__private::unregistered_attribute", reason = "attribute is not in the semantic-convention registry; add it to the registry instead of using `unregistered(…)`" },
    { path = "semlex::__private::extra_attribute", reason = "the signal doesn't define this registry attribute; add it to the signal in the registry instead of using `extra(…)`" },
]
```

Approve a use in the macro, with the reason:
`extra(key, reviewed: "why"): value` or
`unregistered("key", reviewed: "why"): value`. (`#[allow(deprecated,
clippy::disallowed_methods)]` on the `let` or item works too.)
`scripts/escape-report.sh` lists every use and approval for review.
